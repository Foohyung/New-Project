# FitFlow — สิทธิ์ตามบทบาท (RBAC)

ตาม §10.2 และ §17 ของ[มาตรฐาน](../../../docs/ENGINEERING-STANDARD.md) · คอลัมน์แสดงสิทธิ์เริ่มต้นของ role ก่อน admin ปรับแต่งที่ `/roles` · นิยาม permission อยู่ใน `src/api/services/auth/auth/auth.roles.ts`

- ทุกฟังก์ชันใน `src/api/dal/<เรื่อง>/<เรื่อง>/<เรื่อง>.dal.ts` ตรวจสิทธิ์เองก่อนอ่าน/เขียนข้อมูล (หน้าเว็บตรวจซ้ำเพื่อ UX เท่านั้น)
- สมาชิกเข้าถึงข้อมูลได้เฉพาะของตัวเอง โดยระบบใช้ `memberId` จาก session ไม่ใช่จาก URL (กัน IDOR)
- เทรนเนอร์จัดการได้เฉพาะคิว PT ของตัวเอง (ตรวจ ownership ใน DAL)
- `sales.use` เป็น permission ปกติที่ admin เปิด/ปิดให้ทุก role ได้ · ผู้ที่ไม่มี `products.manage` เห็นและยกเลิกได้เฉพาะบิลของตัวเอง (และยกเลิกได้เฉพาะบิลวันนี้)
- สินค้าและสต็อกแยกตามสาขา; พนักงานเห็นและแก้ได้เฉพาะสาขาตัวเอง · admin เห็นภาพรวมและเข้าไปจัดการรายสาขาได้ · POS ใช้สต็อกของสาขาที่บัญชีสังกัด

## กติกาเพิ่มเมนูและสิทธิ์ใหม่

เมนูหรือฟีเจอร์ใหม่ที่มีการควบคุมการเข้าถึง **ต้องกำหนดเป็น permission และตั้งค่าได้จาก `/roles`** เพื่อให้ admin เลือก role ที่เข้าถึงได้ โดยถือเป็นค่าเริ่มต้นของงานพัฒนาทุกครั้ง ห้ามผูกการมองเห็นหรือการใช้งานกับชื่อ role แบบ hard-code แทน permission

เมื่อเพิ่มเมนู/ฟีเจอร์ ให้ทำให้ครบทุกจุด:

1. เพิ่ม permission ใน `PERMISSIONS` และคำอธิบายใน `PERMISSION_LABEL` ที่ `src/api/services/auth/auth/auth.roles.ts`
2. เพิ่ม permission ในหมวดของตัวแก้ไข role (`PERMISSION_GROUPS`) ที่ `src/web/components/roles/roles/roles.forms.tsx` เพื่อให้ admin เลือกได้
3. กำหนดค่าเริ่มต้นของ role ระบบใน `DEFAULT_ROLE_PERMISSIONS` โดยไม่บังคับ role ที่ admin ปรับแต่งเอง
4. ผูกเมนูและหน้าเข้ากับ permission เดียวกัน และตรวจซ้ำใน DAL/Server Action ก่อนอ่านหรือเปลี่ยนข้อมูล
5. เพิ่ม/ปรับการทดสอบให้ยืนยันว่า admin มอบและถอน permission ได้ และ role ที่ไม่มี permission เข้าเมนูหรือเรียกข้อมูลไม่ได้
6. อัปเดตตารางสิทธิ์และเอกสารที่เกี่ยวข้องในไฟล์นี้

admin เปิด/ปิด permission ทุกตัวให้ role ที่แก้ไขได้ รวมถึง `roles.manage`, `branches.manage`, `access.view` และ `payments.configure` ได้ โดยไม่กรองสิทธิ์ซ้ำตามชื่อ role · role `admin` ยังคงป้องกันการแก้ไข/ลบเพื่อไม่ให้ระบบล็อกผู้ดูแลออก · ขอบเขตข้อมูลยังจำกัดตามสาขาและ ownership ตามที่ระบุด้านล่าง

**แดชบอร์ด admin:** ค่าเริ่มต้นรวมข้อมูลทุกสาขา และเลือกดูทีละสาขาจากตัวกรองด้านบนได้ · ข้อมูลจัดเข้าสาขาตามบัญชีผู้สร้างรายการ (`createdById` → `users.branch`) สำหรับสมาชิก เช็กอิน ชำระเงิน และคลาส · รายการที่ไม่มีบัญชีผู้สร้างที่ระบุสาขายังนับในภาพรวม แต่ไม่อยู่ในยอดเมื่อเลือกสาขา · ความจุแสดงเฉพาะเมื่อเลือกสาขา เพราะยังไม่มีการกำหนดความจุต่อสาขา

**ผู้ดูแลระบบและเจ้าของ:** เพิ่มบัญชีที่ `/users` · dropdown บทบาทโหลดจาก role definitions ในฐานข้อมูลและแยกกลุ่มบทบาทระบบ/บทบาทที่สร้างเอง · หากยังไม่มี custom role ให้ admin สร้างที่ `/roles` ก่อน แล้วกลับมาเลือกได้ทันที · รหัสผ่านเก็บเป็น scrypt hash · การสร้างบัญชีถูกบันทึกใน audit log

**แยกตามสาขา (`users.manage`):** สาขาเทียบจากฟิลด์ `branch` ของบัญชี ตรวจใน `src/api/dal/users/users/users.dal.ts`
- **เจ้าของ (และ role อื่นที่ไม่ใช่ admin):** เห็นและเพิ่มบัญชีได้เฉพาะพนักงานในสาขาที่ตัวเองดูแล (ไม่เห็นบัญชี admin) — เจ้าของ 1 คนดูแลได้หลายสาขา: สาขาหลัก = `users.branch` สาขาเพิ่มเติมอยู่ในตาราง `owner_branches` ถ้ามีมากกว่า 1 สาขาจะมีแท็บเลือกสาขาที่ `/users` และช่องสาขาในฟอร์มเพิ่มบัญชีเป็น dropdown ให้เลือกเฉพาะสาขาที่ดูแล — DAL บังคับใช้สาขาจาก session เสมอ ส่งสาขาอื่นมาก็ถูกเพิกเฉย · มอบ role `admin` ไม่ได้ (dropdown ไม่แสดง และ DAL ปฏิเสธ `INVALID_USER_ROLE`)
- **admin:** ตาราง `/users` แสดงเฉพาะบัญชี admin และเจ้าของ (พร้อมสาขาที่ดูแลและจำนวนพนักงาน) พนักงานอื่นดูผ่านหน้าเจ้าของ — กดรูปดวงตาท้ายแถวเจ้าของเพื่อเปิด `/users/<id>` — เห็นทุกสาขาที่เจ้าของคนนั้นดูแลและพนักงานในแต่ละสาขา เพิ่ม/เอาสาขาเพิ่มเติมออกได้ (สาขาหลักเอาออกไม่ได้ · บันทึก audit `owner.branch.add` / `owner.branch.remove`)
- **admin:** เพิ่มบัญชีให้สาขาใดก็ได้ — ช่องสาขาเป็น dropdown จากตาราง `branches` (เฉพาะสาขาที่เปิดใช้งาน) · DAL ปฏิเสธชื่อสาขาที่ไม่มีในตาราง (`UNKNOWN_BRANCH`) กันพิมพ์ผิดแล้วกลายเป็นสาขาใหม่

**สาขา (`/branches`, `branches.manage`):** ตาราง `branches` เป็นข้อมูลหลักของสาขา (ชื่อ เบอร์โทร ที่อยู่ สถานะใช้งาน) · ตารางและ dropdown สาขาเรียงตามลำดับที่เพิ่ม (สาขาแรกอยู่บนสุด) · ตารางอื่นอ้างสาขาด้วยชื่อ (`users.branch`, `owner_branches.branch`, `branch_branding.branch`, `products.branch`) — **เปลี่ยนชื่อสาขา** อัปเดตข้อมูลที่อ้างสาขาใน transaction เดียว · **ปิดใช้งาน** = ไม่แสดงให้เลือกตอนเพิ่มบัญชีใหม่ บัญชีเดิมใช้งานต่อได้ · **ลบ** ได้เฉพาะสาขาที่ไม่มีบัญชีผู้ใช้หรือสินค้า (`BRANCH_IN_USE`) และลบสาขาเพิ่มเติมของเจ้าของกับแบรนด์ของสาขานั้นไปด้วย · ตรวจ permission ซ้ำใน DAL · บันทึก audit `branch.create` / `branch.update` (before/after) / `branch.delete`

**แบรนด์สาขา (`/branding`):** admin เห็นภาพรวมทุกสาขาและเลือกสาขาเพื่อแก้ชื่อ Gym สี และโลโก้ได้ · owner จัดการได้เฉพาะสาขาของตัวเอง · DAL ตรวจขอบเขตสาขา และโลโก้ที่อัปโหลดอ่านได้เฉพาะ admin หรือผู้ใช้ในสาขานั้น
- **แก้ไข/ลบบัญชี:** เฉพาะ admin (`updateManagedUser` / `deleteManagedUser` ตรวจ role ใน DAL) · เปลี่ยนรหัสผ่านหรือปิดใช้งาน = ลบ session ของบัญชีนั้นทุกเครื่อง · admin เปลี่ยน role ตัวเอง ปิดใช้งาน ตั้งช่วงวันที่ หรือลบบัญชีตัวเองไม่ได้ (`USER_SELF_LOCKOUT`) · บันทึก audit `user.update` (before/after ไม่มีรหัสผ่าน) และ `user.delete`
- **active from / active to:** ช่วงวันที่บัญชีใช้งานได้ (รวมทั้งสองวัน ตามเวลาไทย · null = ไม่จำกัด) ตรวจทั้งตอนเข้าสู่ระบบ (`verifyCredentials`) และทุก request (`getSession`) ด้วย `accountUsable` ใน `auth.service.ts` — พ้นวัน active to แล้ว session ที่ค้างอยู่ใช้ไม่ได้ทันที
- test: `src/api/test/users/users/users.dal.test.ts` (ต้องตั้ง `TEST_DATABASE_URL`)

**admin:** จัดการชื่อ role และ permission ได้ที่ `/roles` · ทุก role (รวม `member`, `trainer` และ custom role) เลือก permission ระบบได้เหมือนกัน · permission ที่กำหนดในฐานข้อมูลเป็นตัวตัดสินการเข้าถึง; `roles.manage` ให้จัดการ role อื่นได้ แต่ role `admin` ยังคงแก้ไข/ลบไม่ได้ · custom role ลบได้เมื่อไม่มีบัญชีผูกอยู่ · ผู้ได้รับ `branches.manage` จัดการสาขาทั้งระบบได้ · ผู้ได้รับ `access.view` อ่าน audit log พร้อม IP ได้ · `payments.configure` จำกัด admin ทุกสาขา, owner สาขาที่ดูแล และ role อื่นสาขาตัวเอง · การให้ permission สมาชิกหรือการเงินเปิดการเข้าถึงตามสิทธิ์นั้น · บัญชีที่ผูก `trainerId` ยังคงจัดการ PT ได้เฉพาะของเทรนเนอร์ตัวเอง

หน้า `/roles` ให้เลือก role จากแท็บด้านบนก่อน แล้วแสดงข้อมูลและฟอร์มของ role นั้น · ปุ่ม **เพิ่ม role** เปิดฟอร์มสร้างใหม่ · ฟอร์มแก้ไข role มีตัวกรองหมวดสิทธิ์, ค้นหาตามชื่อหรือรหัส permission และตัวเลือกดูเฉพาะสิทธิ์ที่เลือกแล้ว สิทธิ์ที่แสดงเป็น permission ของระบบซึ่งเชื่อมกับเมนูและการทำงานจริง ผู้ดูแลกำหนดชุดสิทธิ์ให้ role ใดก็ได้ แต่ `roles.manage` แสดง/มอบได้เฉพาะ `admin`

หลัง deploy การเปลี่ยนแปลง role ครั้งแรก ให้รัน `pnpm db:migrate` เพื่อสร้าง role definitions จาก role ปัจจุบันก่อนใช้งาน `/roles`

**เจ้าของ:** ตั้งชื่อ Gym (แสดงเด่นกว่า FitFlow) สีหลัก และโลโก้ของสาขาตัวเองที่ `/branding` ได้ทั้ง URL HTTPS และอัปโหลดไฟล์ PNG/JPEG/WebP (ไม่เกิน 5 MB)
**ลบสมาชิก:** เฉพาะ admin และเจ้าของ (`canDeleteMember` ใน `members.dal.ts`) — ลบถาวรพร้อมบัญชีเข้าสู่ระบบของสมาชิก การชำระเงิน/ใบเสร็จ เช็กอิน การจอง และการแจ้งเตือน · บันทึก audit `member.delete` (รหัส ชื่อ เบอร์ จำนวนรายการชำระ) · แก้ไขข้อมูลติดต่อใช้ `members.manage` และมี popup ยืนยันก่อนบันทึก
**แยกหน้าที่ (separation of duties):** เคาน์เตอร์รับเงินได้แต่ยืนยันสลิปโอนเองไม่ได้ ต้องให้ผู้จัดการหรือเจ้าของยืนยัน · เคาน์เตอร์ใช้คูปองตอนรับชำระได้ (`payments.collect`) แต่สร้างคูปองเองไม่ได้ · สั่งรอบตัดบัตรได้เฉพาะ `payments.confirm`

**สมาชิกเช็กอินเอง:** ปุ่ม "เช็กอินเข้ายิม" ในหน้า `/me` (`selfCheckIn` ใน `members.dal.ts`) ใช้ `memberId` จาก session เท่านั้น · กติกาเดียวกับเคาน์เตอร์ (หมดอายุ/พักสมาชิก = ไม่ผ่าน และบันทึกเป็นเช็กอินที่ถูกปฏิเสธ) · กดซ้ำภายใน 60 นาทีไม่นับเพิ่ม · audit `checkin.self` / `checkin.self.rejected` · ⚠️ ยังไม่ตรวจว่าสมาชิกอยู่ที่ยิมจริง (กดจากที่ไหนก็ได้)

**PDPA:** ข้อความแจ้งเตือน/การตลาดส่งเฉพาะสมาชิกที่ติ๊กยินยอมรับข่าวสาร (แยกจากความยินยอมใช้บริการ)

**บังคับเปลี่ยนรหัสผ่าน:** บัญชีที่ admin/เจ้าของสร้างจากหน้าจัดการบัญชี และบัญชีสมาชิกที่สร้างตอนสมัครด้วยรหัสเริ่มต้น `12345678` มี `must_change_password = true` — ใส่รหัสถูกแล้วหน้า `/login` เปลี่ยนเป็นขั้นที่ 2 "ตั้งรหัสผ่านใหม่" ทันที (ไม่มีเมนูของระบบ) และทุกหน้า/Server Action ที่เรียก `requireSession()` จะพากลับมาที่ขั้นนี้จนกว่าจะตั้งรหัสใหม่อย่างน้อย 8 ตัว (ไม่ซ้ำรหัสเดิม) · เปลี่ยนแล้วออกจากระบบทุกเครื่อง (รวมเครื่องนี้) ต้องเข้าสู่ระบบใหม่ด้วยรหัสใหม่ · บันทึก audit `auth.password.change`

**ลืมรหัสผ่าน:** ลิงก์ "ลืมรหัสผ่าน?" ที่หน้า `/login` → `/forgot-password` (ไม่ต้องเข้าสู่ระบบ) ส่งคำขอด้วยอีเมล/เบอร์ — ตอบข้อความเดียวกันเสมอไม่บอกว่าบัญชีมีจริงไหม · มีคำขอค้างแล้วไม่สร้างซ้ำ · ไม่รับคำขอของ admin · คำขอขึ้นที่การ์ด "คำขอรีเซ็ตรหัสผ่าน" หน้า `/users` (admin เห็นทุกสาขา เจ้าของเห็นเฉพาะสาขาที่ดูแล) → ตรวจตัวตนแล้วกด "รีเซ็ตรหัสผ่าน" = รหัสชั่วคราว `12345678` + บังคับเปลี่ยน + ออกจากระบบทุกเครื่อง · บันทึก audit `user.password.reset` · ยังไม่มีการส่ง SMS/อีเมล

**บทบาทมาจากบัญชี:** ผู้ใช้เลือกบทบาทเองไม่ได้ — เข้าสู่ระบบที่ `/login` แล้วระบบอ่านบทบาทจากบัญชี (`src/api/lib/auth/auth/auth.accounts.ts`) · session เก็บฝั่ง server cookie `ff-session` มีแค่ token สุ่ม (httpOnly) · ใส่ผิด 5 ครั้งล็อก 15 นาที · **ระยะที่ 2:** ย้ายบัญชีและ session ไป Better Auth + 2FA สำหรับพนักงาน

## เปิดหน้าที่ไม่มีสิทธิ์

- เมนูซ่อนหน้าที่ไม่มีสิทธิ์อยู่แล้ว ถ้าพิมพ์ URL เองหรือกดลิงก์เก่า หน้าจะเรียก `accessDenied()` (`src/web/app/layout/layout/layout.access-denied.tsx`)
- ระบบพากลับ**หน้าก่อนหน้า** (จาก Referer และคง query เดิม) ถ้าไม่มี ให้ไปหน้าแรกของตำแหน่ง (`landingFor`) พร้อม `?denied=1` แล้วขึ้นแจ้งเตือนสีแดง "บัญชีนี้ไม่มีสิทธิ์เปิดหน้านั้น"
- กันวนซ้ำ: `proxy.ts` ส่ง `x-pathname` ให้รู้หน้าปัจจุบัน ถ้าหน้าที่จะกลับไปคือหน้าเดิม จะแสดงกล่อง "ไม่มีสิทธิ์เข้าถึง" แทน
- ข้อมูลยังถูกกันใน DAL ทุก query เหมือนเดิม (`authorize`) · Server Action / export ที่ไม่มีสิทธิ์ยังตอบ 403
