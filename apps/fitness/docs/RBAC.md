**ผู้ดูแลระบบและเจ้าของ:** เพิ่มบัญชีที่ `/users` · dropdown บทบาทโหลดจาก role definitions ในฐานข้อมูลและแยกกลุ่มบทบาทระบบ/บทบาทที่สร้างเอง · หากยังไม่มี custom role ให้ admin สร้างที่ `/roles` ก่อน แล้วกลับมาเลือกได้ทันที · รหัสผ่านเก็บเป็น scrypt hash · การสร้างบัญชีถูกบันทึกใน audit log

**แยกตามสาขา (`users.manage`):** สาขาเทียบจากฟิลด์ `branch` ของบัญชี ตรวจใน `src/api/dal/users/users/users.dal.ts`
- **เจ้าของ (และ role อื่นที่ไม่ใช่ admin):** เห็นและเพิ่มบัญชีได้เฉพาะพนักงานในสาขาที่ตัวเองดูแล (ไม่เห็นบัญชี admin) — เจ้าของ 1 คนดูแลได้หลายสาขา: สาขาหลัก = `users.branch` สาขาเพิ่มเติมอยู่ในตาราง `owner_branches` ถ้ามีมากกว่า 1 สาขาจะมีแท็บเลือกสาขาที่ `/users` — DAL บังคับใช้สาขาจาก session เสมอ ส่งสาขาอื่นมาก็ถูกเพิกเฉย · มอบ role `admin` ไม่ได้ (dropdown ไม่แสดง และ DAL ปฏิเสธ `INVALID_USER_ROLE`)
- **admin:** ตาราง `/users` แสดงเฉพาะบัญชี admin และเจ้าของ (พร้อมสาขาที่ดูแลและจำนวนพนักงาน) พนักงานอื่นดูผ่านหน้าเจ้าของ — กดรูปดวงตาท้ายแถวเจ้าของเพื่อเปิด `/users/<id>` — เห็นทุกสาขาที่เจ้าของคนนั้นดูแลและพนักงานในแต่ละสาขา เพิ่ม/เอาสาขาเพิ่มเติมออกได้ (สาขาหลักเอาออกไม่ได้ · บันทึก audit `owner.branch.add` / `owner.branch.remove`)
- **admin:** เพิ่มบัญชีให้สาขาใดก็ได้
- **แก้ไข/ลบบัญชี:** เฉพาะ admin (`updateManagedUser` / `deleteManagedUser` ตรวจ role ใน DAL) · เปลี่ยนรหัสผ่านหรือปิดใช้งาน = ลบ session ของบัญชีนั้นทุกเครื่อง · admin เปลี่ยน role ตัวเอง ปิดใช้งาน ตั้งช่วงวันที่ หรือลบบัญชีตัวเองไม่ได้ (`USER_SELF_LOCKOUT`) · บันทึก audit `user.update` (before/after ไม่มีรหัสผ่าน) และ `user.delete`
- **active from / active to:** ช่วงวันที่บัญชีใช้งานได้ (รวมทั้งสองวัน ตามเวลาไทย · null = ไม่จำกัด) ตรวจทั้งตอนเข้าสู่ระบบ (`verifyCredentials`) และทุก request (`getSession`) ด้วย `accountUsable` ใน `auth.service.ts` — พ้นวัน active to แล้ว session ที่ค้างอยู่ใช้ไม่ได้ทันที
- test: `src/api/test/users/users/users.dal.test.ts` (ต้องตั้ง `TEST_DATABASE_URL`)

**admin:** จัดการชื่อ role และ permission ได้ที่ `/roles` · ทุก role (รวม `member`, `trainer` และ custom role) เลือก permission ระบบได้เหมือนกัน · การตรวจสิทธิ์ใช้ permission ที่กำหนดในฐานข้อมูลโดยตรง ไม่มีการกรองสิทธิ์เพิ่มตามชื่อ role · `roles.manage` สงวนให้ `admin` · role ระบบแก้ไขได้แต่ลบไม่ได้ · custom role ลบได้เมื่อไม่มีบัญชีผูกอยู่ · `admin` เป็น role ป้องกัน แก้ไข/ลบไม่ได้ · การให้ `members.view`, `members.manage` หรือ permission การเงินทำให้บัญชีเข้าถึงข้อมูล/การทำงานตาม permission นั้น · บัญชีที่ผูก `trainerId` ยังคงจัดการ PT ได้เฉพาะของเทรนเนอร์ตัวเอง

หน้า `/roles` ให้เลือก role จากแท็บด้านบนก่อน แล้วแสดงข้อมูลและฟอร์มของ role นั้น · ปุ่ม **เพิ่ม role** เปิดฟอร์มสร้างใหม่ · ฟอร์มแก้ไข role มีตัวกรองหมวดสิทธิ์, ค้นหาตามชื่อหรือรหัส permission และตัวเลือกดูเฉพาะสิทธิ์ที่เลือกแล้ว สิทธิ์ที่แสดงเป็น permission ของระบบซึ่งเชื่อมกับเมนูและการทำงานจริง ผู้ดูแลกำหนดชุดสิทธิ์ให้ role ใดก็ได้ แต่ `roles.manage` แสดง/มอบได้เฉพาะ `admin`

หลัง deploy การเปลี่ยนแปลง role ครั้งแรก ให้รัน `pnpm db:migrate` เพื่อสร้าง role definitions จาก role ปัจจุบันก่อนใช้งาน `/roles`

**เจ้าของ:** ตั้งชื่อ Gym (แสดงเด่นกว่า FitFlow) สีหลัก และโลโก้ของสาขาตัวเองที่ `/branding` ได้ทั้ง URL HTTPS และอัปโหลดไฟล์ PNG/JPEG/WebP (ไม่เกิน 5 MB)
**ลบสมาชิก:** เฉพาะ admin และเจ้าของ (`canDeleteMember` ใน `members.dal.ts`) — ลบถาวรพร้อมบัญชีเข้าสู่ระบบของสมาชิก การชำระเงิน/ใบเสร็จ เช็กอิน การจอง และการแจ้งเตือน · บันทึก audit `member.delete` (รหัส ชื่อ เบอร์ จำนวนรายการชำระ) · แก้ไขข้อมูลติดต่อใช้ `members.manage` และมี popup ยืนยันก่อนบันทึก
**แยกหน้าที่ (separation of duties):** เคาน์เตอร์รับเงินได้แต่ยืนยันสลิปโอนเองไม่ได้ ต้องให้ผู้จัดการหรือเจ้าของยืนยัน · เคาน์เตอร์ใช้คูปองตอนรับชำระได้ (`payments.collect`) แต่สร้างคูปองเองไม่ได้ · สั่งรอบตัดบัตรได้เฉพาะ `payments.confirm`

**สมาชิกเช็กอินเอง:** ปุ่ม "เช็กอินเข้ายิม" ในหน้า `/me` (`selfCheckIn` ใน `members.dal.ts`) ใช้ `memberId` จาก session เท่านั้น · กติกาเดียวกับเคาน์เตอร์ (หมดอายุ/พักสมาชิก = ไม่ผ่าน และบันทึกเป็นเช็กอินที่ถูกปฏิเสธ) · กดซ้ำภายใน 60 นาทีไม่นับเพิ่ม · audit `checkin.self` / `checkin.self.rejected` · ⚠️ ยังไม่ตรวจว่าสมาชิกอยู่ที่ยิมจริง (กดจากที่ไหนก็ได้)

**PDPA:** ข้อความแจ้งเตือน/การตลาดส่งเฉพาะสมาชิกที่ติ๊กยินยอมรับข่าวสาร (แยกจากความยินยอมใช้บริการ)

**บังคับเปลี่ยนรหัสผ่าน:** บัญชีที่ admin/เจ้าของสร้างจากหน้าจัดการบัญชี และบัญชีสมาชิกที่สร้างตอนสมัครด้วยรหัสเริ่มต้น `12345678` มี `must_change_password = true` — ใส่รหัสถูกแล้วหน้า `/login` เปลี่ยนเป็นขั้นที่ 2 "ตั้งรหัสผ่านใหม่" ทันที (ไม่มีเมนูของระบบ) และทุกหน้า/Server Action ที่เรียก `requireSession()` จะพากลับมาที่ขั้นนี้จนกว่าจะตั้งรหัสใหม่อย่างน้อย 8 ตัว (ไม่ซ้ำรหัสเดิม) · เปลี่ยนแล้วออกจากระบบทุกเครื่อง (รวมเครื่องนี้) ต้องเข้าสู่ระบบใหม่ด้วยรหัสใหม่ · บันทึก audit `auth.password.change`

**ลืมรหัสผ่าน:** ลิงก์ "ลืมรหัสผ่าน?" ที่หน้า `/login` → `/forgot-password` (ไม่ต้องเข้าสู่ระบบ) ส่งคำขอด้วยอีเมล/เบอร์ — ตอบข้อความเดียวกันเสมอไม่บอกว่าบัญชีมีจริงไหม · มีคำขอค้างแล้วไม่สร้างซ้ำ · ไม่รับคำขอของ admin · คำขอขึ้นที่การ์ด "คำขอรีเซ็ตรหัสผ่าน" หน้า `/users` (admin เห็นทุกสาขา เจ้าของเห็นเฉพาะสาขาที่ดูแล) → ตรวจตัวตนแล้วกด "รีเซ็ตรหัสผ่าน" = รหัสชั่วคราว `12345678` + บังคับเปลี่ยน + ออกจากระบบทุกเครื่อง · บันทึก audit `user.password.reset` · ยังไม่มีการส่ง SMS/อีเมล

**บทบาทมาจากบัญชี:** ผู้ใช้เลือกบทบาทเองไม่ได้ — เข้าสู่ระบบที่ `/login` แล้วระบบอ่านบทบาทจากบัญชี (`src/api/lib/auth/auth/auth.accounts.ts`) · session เก็บฝั่ง server cookie `ff-session` มีแค่ token สุ่ม (httpOnly) · ใส่ผิด 5 ครั้งล็อก 15 นาที · **ระยะที่ 2:** ย้ายบัญชีและ session ไป Better Auth + 2FA สำหรับพนักงาน
